## Assets and adversary

The protected assets are user workspaces, model/Git credentials, mTLS executor
images, snapshots, other tenants' identities and Kubernetes control-plane
authority. Treat the browser, extension, terminal, workspace files, Agent
prompts, skill repositories and commands generated by OpenCode as untrusted.

OpenCode session sharing and AI SDK OpenTelemetry are disabled. The runtime
exposes only the administrator-defined `model-proxy` provider and does not
download the public model catalog.

The design addresses a malicious or compromised user workload. It does not
protect against a malicious cluster administrator, compromised Kubernetes
control plane, compromised JupyterHub identity provider, or a container-runtime
escape.

## Enforced boundaries

- JupyterHub is the canonical identity source. The mediator never trusts a
  username, namespace, PVC, or Agent resource name supplied by the client.
- The workspace mapping is an administrator-owned allowlist.
- The code-server pod has ServiceAccount automount disabled and no kubeconfig.
  Its JupyterHub token reaches only the mediator, which resolves the canonical
  username and performs all Kubernetes operations.
- Only the mediator writes Agent/Task resources and credential-free state.
- Agent and Task pods use a zero-permission ServiceAccount with token automount
  disabled.
- Agent containers run non-root, drop all capabilities, forbid privilege
  escalation, use RuntimeDefault seccomp and a read-only root filesystem.
- Writable temporary volumes and CPU, memory, ephemeral storage and duration
  are bounded.
- The Agent mounts one configured PVC subpath. It never mounts the snapshot PVC,
  JupyterHub token, kubeconfig, node socket, host path, or general Secret set.
- NetworkPolicy is default-deny and uses immutable workspace labels to separate
  users sharing a namespace. The Agent policy allows DNS, same-workspace pods,
  and the configured model-gateway namespace. It does not select one gateway
  pod or port and cannot require TLS; the gateway must enforce client
  authentication and model authorization. Kubernetes policies cannot filter DNS
  names, so external providers must be reached through an egress gateway.
- Production workspaces can enable `modelMTLS`. OpenCode then uses plaintext
  HTTP on pod loopback and an embedded proxy establishes TLS 1.3 to the gateway,
  validates its CA/hostname, and presents a client certificate. This protects
  and authenticates only the proxy-to-gateway hop.

## mTLS identity and authorization boundary

The JupyterHub identity and mTLS identity are independent. JupyterHub proves a
canonical user to the mediator; the client certificate proves possession of the
certificate identity embedded in the executor image to the model gateway.
Sharing an image necessarily shares that identity, while distinct image digests
alone do not prove distinct certificates.

Every process in the Agent pod can call the loopback proxy and exercise its
certificate. The proxy does not prove that a request came from OpenCode, and
`allowedModels` does not prevent a command from sending another request through
the same local endpoint. The gateway remains responsible for route/model/quota
authorization and must reject direct connections without an accepted client
certificate.

The AES-256-GCM bundle prevents casual PEM/`strings` inspection, but the key and
decryptor remain in the binary. This is inspection resistance, not a key vault,
hardware-backed identity, service-mesh identity, or non-exportable workload
credential.

## Secrets

Raw model API keys and private Git credentials are created by administrators as
Kubernetes Secrets and referenced by name. They are not accepted by the
extension API, terminal forwarding, Helm values, ConfigMaps, workspace PVC, or
logs.

The optional mTLS private key is different: it is injected at image build time,
not mounted from a runtime Kubernetes Secret. The final executor binary and
image must be distributed, retained, rotated, and revoked as secret-bearing
artifacts. Deleting a Kubernetes Secret cannot revoke that embedded identity.

The mediator logs identifiers and bounded errors only. It must never log bearer
headers, prompts, request bodies, provider responses, URLs with query strings,
or environment values.

## Residual risks

- Direct interactive editing has no automatic pre-session snapshot or workspace
  Lease. The same user must avoid editing the same files concurrently in VS Code
  and OpenCode. Use the optional Task API when transactional snapshot/restore is
  required.
- `ReadWriteOnce` behavior varies by CSI driver and topology. Prefer RWX or prove
  simultaneous mounts on the target cluster.
- Registry skills, custom Git skills, and npm plugins execute inside the Agent
  trust boundary. Administrators curate Registry entries; users may additionally
  attach up to five public HTTPS skill repositories without credentials. Required
  skills are re-applied server-side and cannot be removed by a client payload.
  Pin immutable refs and review their content.
- KubeOpenCode uses a `v1alpha1` API. An upstream upgrade may alter security or
  schema semantics and requires full revalidation.
- The mTLS proxy has no dedicated health probe or process supervisor. Agent
  readiness does not prove model egress is healthy.
- The mediator is single-replica until leader election is implemented.

## Production requirements

Enable Kubernetes audit logs, Secret encryption at rest, Pod Security Admission
at `restricted`, image signature/digest policy, vulnerability scanning, runtime
monitoring, resource quotas, LimitRanges, and tested backup/restore for PVCs.
The model gateway must additionally require client certificates, authorize the
exact certificate identity, enforce model/route/quota policy, expose expiry and
authentication-failure monitoring, and support revocation.
